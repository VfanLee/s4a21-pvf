# 点券商城

## 修改边界与回读

- 引用链：商品 ID → 物品 ID → 登记/定义 → 嵌套奖励或契约映射。
- 只上架不改道具定义；只改价格或页面时保留其他列、支付限制与无关段。
- 整个客户端大类可能对应多个段，修改前明确完整范围。
- 回读字段数、编号冲突、辅助引用及范围外内容；页面、扣款和发货分别验收。

A21 的商品目录定位到 `etc/cerashop.etc`。外部书签中的 `etc/newcashshop.etc`、
`etc/newcashshop_restrict.etc` 不证明它们是参考 ServerS4A21 的商品或限购入口；
应查实际目录段和读取方，不能补建或替换为其他版本的文件。

对应 [cera-shop 技能](../../.agents/skills/cera-shop/SKILL.md)。道具定义和礼包奖励见
[items.md](items.md)，NPC 商店见 [npc-shop.md](npc-shop.md)。

## 商品编号、物品编号和价格

`etc/cerashop.etc` 是“商品 ID → 物品 ID”。购买请求用商品 ID；物品 ID 要通过
`stackable/stackable.lst` 或 `equipment/equipment.lst` 找定义文件。
改道具的 `[cash]`、`[price]` 或名字，不会设置商城的点券售价。

下表列号从 **1** 开始；反引号内带空格的文本仍算一个字段。保留非目标列。

| 段 | 每条字段数 | 点券售价列 | 已确认的其他字段 |
| --- | --- | --- | --- |
| `[item]`、`[premium]`、`[creature]`、`[coin]`、`[material]`、`[recoveryitem]` | 9 | 6 | 商品 ID 第 1 列，物品 ID 第 2 列，数量第 3 列，金币第 4 列；第 5 列胜点当前目录读取器未实现 |
| `[visual]` | 8 | 6 | 商品第 1 列，物品第 2 列，数量第 3 列，时长天数第 4 列 |
| `[package]`、`[regular package]`、`[community package]` | 11 | 5 | 商品第 1 列，物品第 2 列，数量第 3 列；第 4 列不是金币价格 |
| `[avatar]` | 6 | 6 | 商品第 1 列，物品第 2 列；第 3 列为从 1 开始的装扮购买档位 |
| `[selectable character premium]` | 9 | 6 | 商品第 1 列，物品第 2 列，时长第 4 列；目录数量固定为 1 |
| `[charac premium package]` | 9 | 3 | 商品第 1 列，物品第 2 列，时长第 8 列；目录数量固定为 1 |

装扮购买还会读取 `.equ` 的 `[avatar type select]`：每档以七个数字字段开始，时长在第 1 列，点券价在第 4 列。
数字档位后可能有镶嵌槽描述，修改时保留。
解析到的档位价格为正数时，会覆盖商品表中的价格。修改装扮售价或时长前，同时核对商品档位和装备定义。

`[buy only cera]` 和 `[buy only cera point]` 内是**物品 ID**，控制支付限制。
未要求修改时保留支付限制；完整读取目标段，字段数损坏时先解决再写入。

S4A21 次元彼端 的 `[gift disallowance]` 列出商品 ID；`[btn control]` 每条四个字段，
商品 ID 在第 1 列。`[buy restrict item]` 也是四字段一条，但第 1 列是限制记录编号，
第 2 列才是商品 ID。第 3～4 列未单独确认含义和修改要求时保持原样，不能把限制记录编号
当商品编号匹配。

## 页面和重复商品

检查 `etc/eventcharacter/cerashop.etc` 时，应区分归档中的商品内容和实际购买来源。
参考 ServerS4A21 商城目录读取 `etc/cerashop.etc`（或其本地后备文件），
没有读取 eventcharacter 商城的代码引用。只改活动文件不能证明服务端支持购买；
客户端何时启用该文件仍需另行验证。标准 `[material]` 每条记录九个字段，
换行不划分记录；追加完整记录应放在 `[/material]` 前，保留原有记录。
末尾标志未确认含义时保持原值。新增前解析物品登记，并检查实际商城各段的商品 ID 冲突。

S4A21 次元彼端 商城首页的 `[hotnew sell ipg]` 按“商品编号、展示参数”成对记录。
首页商品消失时，同时核对商品表和此推荐段；恢复被过滤商品时，补回完整原记录，
保留展示参数及顺序，不能只恢复商品行。

S4A21 次元彼端 客户端装扮页的“旧商品顺序”按商城记录顺序展示，“新商品顺序”反向展示；仅修改商品编号不会把展示顺序反过来。要在“新商品顺序”中得到“透明克隆、新套装、旧套装”，记录应按相反顺序写入，同套八个部位也反向写入。仅修复行序时保留商品编号与装备的映射，并在游戏中复核当前选择的排序模式。

回读时，按职业提取商城记录的实际顺序，将其装备 ID 序列反转后，与完整的预期展示序列逐项比较。编号与行序同时递增或递减时，截图不能单独证明排序依据；每次只改变一个排序变量，同时比较“新商品顺序”和“旧商品顺序”。回读通过只能证明配置正确，不能代替游戏内验证。

整理稀有装扮配色时，要同时核对名称中的配色和实际外观；不同部位的 `[variation]` 第二个数字并不一定对应同一种颜色，不能直接用它把全套八件分组。

同名透明克隆可能有不同的最低使用等级或购买档位，去重前核对这些差异。
要求成套分组时保留完整八部位，展示顺序按用户要求，不固定克隆优先。

按发布日期排序时，使用套装在国服的首次发布日期，优先核对官方资料；装备 ID 和文件时间不能作为发布日期。保留资料实际支持的年份、月份或日期精度，无国服日期依据的正常套装放在已知日期套装之后，不猜测补日期。

如果只调整 Type 1 商城段内的整数记录，可以在原有段标记之间替换 type-0 数字 token，保留其他原始 token 和字符串引用。新 PVF 重新打开后，应核对未改动压缩块，以及改动块内的其他文件内容。

A21 的 `[regular package]` 为日常礼包页，`[package]` 为主礼包页，角色服务商品在限时/服务界面。
改完后在游戏里核对页面和显示顺序。

跨页移动：从来源段移除原记录，在目标段按目标格式新增一条，再回读两个段。
商品 ID 要跨全部商城段查重：服务端使用同一个字典，后解析的同号记录会覆盖前面记录。
更换重复商品 ID 前确认新号在最终商城目录里未占用；未授权的物品 ID、价格和其他字段保留。

## 稀有装扮与兑换券

通过 `equipment/equipment.lst` 查 ID，扫描 `avatar/` 和 `at_avatar/` 两类目录。
稀有装扮使用 `[grade] 3`，不能用 `[rarity]` 的数值代替。
按职业和配色核对帽子、头发、脸部、胸部、上衣、下装、腰部、鞋子八个部位；皮肤、光环另算。
同部位的独立羽翼或肩甲要保留，不应按部位重复直接排除。

先解析实际定义和可用职业；去重比较动画职业、外观编号、图层和脚本、可选属性及套装特效索引。
GM/调试专用或无法解析的定义不证明可售；只有本地化占位名称不能判为无效。
稀有克隆有 `[item category]` `clear avatar`，还需核对品质和八个部位，避免混入高级克隆。

参考 ServerS4A21中，兑换券支付（`paymentMode=1`）要求品质 3、购买档位 3，
消耗一张稀有装扮兑换券（`2681594`），点券扣款为 0。
确认 `[avatar type select]` 第三档时长为 0，商城记录使用：

```text
商品ID 物品ID 3 0 0 -1
```

仅上架时保留 `.equ` 原价格和档位数据。兑换券是支付方式；使用点券购买时，正数档位价格仍生效。
实机检查扣券、永久装扮发放、预览，以及当前排序模式下的展示顺序，再确认是否位于第一页。

报告中区分“商品记录存在”“物品定义齐全”“游戏内可见”。追加稀有装扮时，
对照各职业原有装扮的商品编号分组；全局不重号不能证明客户端会显示。
只出现部分商品时，先核对实际商城表、职业/分类筛选和隐藏配置，再决定是否补记录，
避免重复上架。各职业的实际可见页面核对通过后，才能称为上架完成。

## 商城迁移

恢复客户端一个大类时，可能涉及多个商城段，不能直接把整个大类等同于 `[item]`。
先确认完整段范围，再按关联配置实际的商品 ID 或物品 ID 列恢复对应记录，保留其他记录
及顺序。发布前比较范围外的全部商城词元和其他文件内容。与参考内容一致的记录沿用底板
原记录；记录已存在并不证明游戏内可见，不能因显示缺失就重复上架。

交付时分开说明“已核对或恢复的记录数”和“实际变化的记录数”，列明新增商品、
变化字段及关联规则。用户报告缺失的商品若原本就与参考一致，应明确说明配置复原
尚未解决其显示问题，等待实机验证，不能把核对数量当成实际变化数量。

仅迁移上架清单、以修改前底板为兼容边界时，保留底板的道具定义及素材引用。
兼容性检查应以最终实际使用的奖励链为准：不导入定义时，检查底板原有的全部奖励链，
包含可选奖励、带期限奖励、选择礼盒及 `[RANDOMBOX]`，不能只检查固定礼包。
模板奖励链用于记录内容差异；模板独有但不会复制的奖励，不能作为过滤底板兼容商品的理由。
只有获准导入对应定义时，才要求其模板新增奖励依赖也齐全，不自动复制模板定义。

Type 1 字符串偏移只属于各自的 PVF。迁移完整商城时，把所有字符串引用重定位到
底板字符串表，保留原词元类型并核对实际文本，不能直接复制模板偏移。
`[selectable character premium]` 中商品编号为 `-1` 的汇总行应保留；
它不属于可购买的正数商品编号，不给它分配新编号。

修复重复商品编号前，先检查辅助配置是否引用该编号；一个重复编号本身不能明确指向
其中哪款商品。过滤商品的关联配置时，确认商品编号所在列后移除完整记录，
保留其他数值和原有占位项，不按相同数字批量删除。

1. 对照已授权的目标包与待导入包，明确要同步的段、定义文件及价格例外。
2. 区分“缺登记”“缺定义文件”“同号映射冲突”。有上架记录不代表物品可用。
3. 根据 `[package data]`、`[booster info]` 的真实结构，逐层查直接奖励、
   二级礼盒以及装备奖励；记录已访问节点防止循环。报告无法解析的 ID 和不支持的效果。
   只获准替换上架清单时，不自动引入额外定义；必要补充需纳入已确认的修改范围。
4. 迁移缺失 `.stk` 时，把新增登记追加到 `stackable/stackable.lst` **底部**，按导入包登记顺序，
   保留原登记与顺序并查重。可编辑文本中每条 ID/路径单独一行。
5. Type 1 二进制 PVF 保存的是词元，原始空白不保存。参考 PvfLib 回读会规范化空格、换行：
   登记和追加顺序可以保留，显示时每条单独一行无法保证。不要为排版强改文件数据类型。
6. 重新打开输出，核对文件数、新定义、原登记前缀及追加项、商品 ID、目标段和价格例外，
   比较非目标内容，并核对改动清单中的路径与实际内容修改、新增逐一对应。

按原版支持范围精简礼包时，区分当前修改目标和对照包。通过对照包的登记及实际文件，
核对礼包本身与全部嵌套奖励；同 ID 映射到不同路径时单独审查。不支持时移除整条商品，
不要擅自删减奖励。确认无需新增客户端资源前，还要对照保留物品的图片、动画引用；
定义齐全不能单独证明游戏内图片正常。下架无需删除可能被其他系统引用的定义或登记。
保留商品的字段、顺序、价格及其他商城段应保持原样。

核对礼包是否补全时，枚举目标包登记的礼包定义，按不同物品 ID 与全部相关商城段比较。
用“导入商城中目标支持的商品”筛选，只能得到两者交集，不能覆盖目标包的全部礼包。
区分原有上架记录被遗漏，以及两份商城都未上架但已有定义的礼包。
按物品类型及奖励引用链识别，不能只按名字；活动包、占位定义、礼包内层礼盒、
奖励缺失项分别记录。定义引用齐全只说明可进一步审查，不能证明图片、购买行为
正常或已有可沿用的点券售价。

补录原版未上架礼包时，点券价取自商城表，物品的 NPC `[price]` 不是点券售价。
没有原有上架记录的礼包，应按用户指定规则定价，并记录参考商品。比较实际礼包
类型，不能因为都位于 `stackable/cash/` 就认作同一系列。占位名称也不能作为
直接排除依据，要按物品技能说明核对本地化和内容。

礼包商品行的最后一列是职业筛选。已有通用商品可使用 `-1`，沿用已核对的通用
商品格式即可。礼包职业字段缺失或拼写错误时，结合奖励装扮的可用职业确认；
限制互相冲突的礼包先复核，不猜测职业页面。

## 契约和客户端资源

部分同步装扮时，要同时保护保留商品行、实际装备定义和登记关系。即使商品自身
定义已经存在，也要继续检查奖励依赖。参考商城本身也可能有重复商品编号，直接
复制会让购买指向另一件道具；获准重新编号后，单独记录编号变化，其他商品内容、
价格照原规则同步。比较登记路径前统一斜杠和大小写，不重复登记等价路径。

资源缺失要按字段区分。`[avatar package preview info]` 指向礼包展示图，缺少该图
不能直接判定奖励图标或穿戴外观也缺失。分别报告各类检查结果；允许保留缺图商品
时明确记录例外，不静默删减商品。

单项限时契约要同时有商城记录、`.stk` 文件及登记、`etc/premiumlist_new.etc` 中的
“物品 → 服务类型/期限”映射。多令牌礼包必须准确发放全部令牌，每个令牌也有服务映射。
`[charac premium package]` 中的全服务契约使用专用购买流程；跨页移动后，实际购买并检查激活的服务状态。

在客户端 NPK 中核对图标、预览图、掉落外观和装备资源。
实机核对页面、顺序、显示价与扣款、限购、发货、嵌套奖励、契约激活和图片。
