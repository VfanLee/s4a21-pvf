# 材料、消耗品与可堆叠道具

对应 [`.agents/skills/items/SKILL.md`](../../.agents/skills/items/SKILL.md)。
NPC 上架语法见 [npc-shop.md](npc-shop.md)，点券商城商品与契约见 [cera-shop.md](cera-shop.md)。

下面示例是结构骨架。实机 `.stk` 还有未列出字段，**不要把示例粘成完整文件**。已有标签改原值，不要重复添加。

## 目录结构

```text
<解包根>/
├── stackable/
│   ├── stackable.lst
│   ├── material/cubepiece_clear.stk      # 3037 无色小晶块
│   └── cash/safe_upgradekit12.stk        # 10098633 金库升到 200 格
└── equipment/
    └── equipment.lst                     # → .equ
```

## 文件说明

| 文件 | 作用 |
| --- | --- |
| `stackable/stackable.lst` | 可堆叠 ID → `.stk`（材料、药剂、任务物、礼包、徽章等） |
| `stackable/**/*.stk` | 道具定义 |
| `equipment/equipment.lst` | 装备 / 称号 / 装扮 / 宠物 ID → `.equ` |
| `equipment/**/*.equ` | 装备类定义 |
| 目标 `itemshop/*.shp` | NPC 出售时，把 ID 写入 `[item list]`；点券商城使用独立商品表，见商城技能 |

ID 由 `.lst` 映射。改 `[name]` 不会生成新 ID。

`[stackable type]`：`[material]` 通常是材料；药剂常见 `[waste]`。以目标道具原类型为准。不要为改价格而改类型（影响背包分栏和使用规则）。

## 共用字段

材料靠近后自动拾取时，先通过 `stackable/stackable.lst` 确认 ID，再查
`etc/autorooting.etc` 的 `[auto rooting index]` 列表。关闭指定物品的自动拾取时，
只移除对应整数 ID，保留其他条目和结束标签；金币 ID `0` 是独立条目，不能用 `0` 替换
不需要的 ID。客户端加载修改后的 PVF 并重启后，分别验证靠近不自动入包和手动拾取正常。
自动拾取列表与掉落来源分开：当前服务端的 `etc/worlddrop.etc` 按怪物等级选取加权物品池，
可能让材料在不同副本出现。关闭自动拾取不会关闭掉落；日志出现 `GET_ITEM` 只能证明
客户端发起拾取请求，不能证明玩家是否按了拾取键。

| 标签 | 含义 | 注意 |
| --- | --- | --- |
| `[name]` `[explain]` `[flavor text]` | 名称 / 说明 / 风味 | 说明 ≠ 效果 |
| `[price]` | NPC 金币买价 | 普通商店优先用这个 |
| `[value]` | 回收相关数值 | **不是**玩家拿到的回收价，见下方公式 |
| `[add price]` | 兑换时额外金币 | 只在有效 `[need material]` 路径生效 |
| `[need material]` … `[/need material]` | 兑换材料 | **材料 ID、数量**成对；不要和商品自身 ID 混淆 |
| `[attach type]` `[trade limit max]` `[impossible contents]` | 绑定 / 流通限制 | 仿同类样本 |
| `[stack limit]` `[weight]` | 堆叠上限 / 重量 | 提高堆叠前考虑已有堆叠会不会合并 |
| `[minimum level]` `[grade]` `[rarity]` | 等级 / 品质展示 | `grade` ≠ 稀有度 |
| `[icon]` `[field image]` `[icon mark]` | 图标 / 掉落外观 | 改文本不会生成新图 |
| `[expiration date]` | 固定到期时间 | 东八区 |
| `[usable period]` | 获得后有效天数 | 非负整数，从**创建时刻**起算 |
| `[cash]` `[medal]` | 道具元数据 | 不是当前服务端通用的点券 / 胜点定价入口；先追踪实际处理路径 |

## 绑定与交易类型

本项目 A21 PVF 的 `[attach type]` 使用以下取值，不要按英文单词 `trade` 猜测含义。

| 取值 | 含义 |
| --- | --- |
| `[free]` | 不限制 |
| `[sealing]` | 封装 |
| `[trade]` | 不可交易 |
| `[account]` | 帐号绑定 |
| `[trade delete]` | 无法交易、删除 |
| `[sealing trade]` | 封装且不可交易 |

要改成不限制交易，把已有 `[attach type]` 的值改为 `[free]`，保留反引号，不要重复添加标签：

```text
[attach type]
	`[free]`
```

`[trade]` 表示不可交易。其他适用的交易限制需另行核对，不能仅凭这个字段断言所有运行时限制都已解除。

## 买价和回收（普通可堆叠）

- **买入**：优先 `[price]`；没有则用正数 `[value]`；两者都没有 → 商店买价 `0`
- **卖出**：优先 `floor(value / 5)`；没有 `value` 则用正数 `floor(price / 5)`。不要把「想让玩家拿到的钱」填进 `[value]`
- **材料兑换金币**：有效 `[need material]` 时用 `max(0, price + add price)`。**不会**回退 `[value]`；缺 `[price]` 则金币部分为 `0`

| ID | 名称 | 字段 | 买 | 卖 |
| --- | --- | --- | --- | --- |
| `3047` | 林纳斯火炉券 | `price=10000` `value=10` | 10000 | 2 |
| `1006` | 加速药剂 | `2000` / `200` | 2000 | 40 |
| `3037` | 无色小晶块 | 只有 `price=100` | 100 | 20 |
| `3042` | 无色大晶体 | `price=2000` `value=400`，兑换 `3037 × 100` | 兑换金币 2000 | 80 |

装备回收走服务端装备费率，**不能**套 `value ÷ 5`，有最低价。装备买价同样优先 `[price]`，缺省回退 `[value]`；有兑换时用 `price + add price`。

当前服务端的 NPC 兑换只读取 `[need material]` 的前两个数值，即一个“材料 ID、数量”对；不要增加多组材料并期待服务器会扣除。A21 样本使用闭合 `[/need material]`；若某文件没有闭合，跟近邻，不要混用。

把材料兑换改成普通金币购买时，删除完整的 `[need material]` 块及其闭合标签，再修改或新增唯一一份 `[price]`。放在 `[icon]` 前只是排版惯例，不是价格生效条件。保留使用时消耗道具的 `[consume item]`、使用效果、`[value]` 和商店列表。道具定义的价格会影响其他 NPC 出售同一道具；若没有 `[value]`，普通叠加道具的回收价也会按新 `[price]` 回退计算。

### 兑换字段示例

```text
[price]
	2000
[value]
	400
[need material]
	3037 100
[/need material]
```

## 期限

| 标签 | 含义 | 注意 |
| --- | --- | --- |
| `[usable period] 7` | 新实例从创建起 7 天 | |
| `[expiration date]` | 固定时刻 | `` `yyyy-MM-dd HH:mm:ss` ``、`yyyy-MM-dd`、可解析的 `yyyyMMdd` 或 Unix 秒；东八区 |
| `[stat change duration]` | 使用后效果持续 | 常见毫秒；**不是**背包到期 |
| `[cool time]` | 使用冷却 | 常见毫秒；**不是**背包到期 |

两字段同时存在：服务端优先正数 `[usable period]`。到期写在道具**实例**上，改 PVF 不会刷新旧道具。

普通创建与租赁领取要分开看。当前服务端租赁处理器显式设置“当前 Unix 时间 +
`RentalWeaponRequestCodec.RentalDurationSeconds`”，该常量为 86400 秒，并覆盖普通装备期限解析结果。
因此 `.equ` 的可用天数不控制这条租赁领取的实际期限。刚领取就显示过期时，应核对领取路径、
实例时间戳、客户端和服务端时钟以及协议字段解释，不能直接认定是 PVF 写了旧日期。
需要保留租期时，删除可用天数不是修复；未找到相关有效字段前不能承诺仅改 PVF 能解决。

去掉今后新实例的到期：删除整个 `[expiration date]`（不要改成空字符串或随意远期），并确认没有 `[usable period]`。未覆盖时新实例 `ExpireTime=0`。

按名称前缀批量去除武器期限时，先通过 `equipment.lst` 解析，匹配真实 `[name]`，
并确认 `[equipment type]` 为 `[weapon]`；原本无期限的匹配项不用改。
Type 1 文件由五字节令牌组成，只移除期限标签和对应值的令牌，可保留其余令牌与字符串引用。
输出后重新打开，逐文件比较原包与新包的内容，差异仅允许出现在计划路径和移除的期限范围。

例：`490002458` 史诗 Buff 药剂，去掉 `[expiration date]`；保留效果持续和冷却。该文件还有 `[usable event]`、`[item category] event`，去期限不会自动取消活动限制。验收必须**新买一件**。

## 材料

改价格只动价格标签。改用途前先搜该 ID 的配方、任务、商店、兑换。不要把材料改成消耗品类型来「方便上架」。

## 消耗品字段

| 内容 | 常见标签 |
| --- | --- |
| 冷却 | `[cool time]` `[cooltime group]` `[cooltime maintenance]` |
| 效果 | `[hp recovery]` `[mp recovery]` `[stat change]` `[stat change duration]` `[effect maintenance]` |
| 限制 | `[usable job]` `[action usable place]` `[impossible contents]` |
| 次数 / 限购 | `[total usable count]` `[daily purchase limit]` |

效果参数结构因药剂而异：复制同类道具，只改明确了解的数值。说明里写「减冷却」不代表改 `[explain]` 就会改机制（如 `2600021`）。

`2600561` 顶级力量灵药是 `[waste]`，没有 `[price]` / `[value]`，直接上架买价为 0。要收费就加 `[price]`，要回收再设 `[value]`（回收 = value/5）。要 7 天期限则加 `[usable period] 7`。

持续药水效果中，当前服务端发现 `[effect maintenance]` 时，要求 `[stat change duration]` 为正数，并用它计算效果状态的截止时间；`[cool time]` 则是道具再次使用的冷却。本项目 A21 的减技能冷却药水可沿用 `[effect maintenance] 1 1 1 0` 和 ``[stat change duration] 1800000 `myself` `` 的维持配置，无需替换原有特殊效果。调整后仍应检查真实技能冷却、持续时间和切换地图后的效果，不能只看图标，也不能把结果推广到其他未验证的特殊消耗品。

`[cooltime group]` 是道具共用冷却的组号，不是时长，也不是效果分组。同组用于关联冷却，但不会把各道具不同的 `[cool time]` 数值自动统一。当前服务端在启用 `[cooltime maintenance]` 的路径中检查同一道具及同一正数组号的活动冷却；仅添加组号不会启用这条服务端路径。每个冷却字段只保留一份，避免重复定义。

## 其他已存在类型

| 类型 | 怎么认 | 注意 |
| --- | --- | --- |
| 任务物品 | `[stackable type] [quest]`，如 `3072` | 先查任务引用 |
| 副职业材料 | `[material expert job]`，如 `2610045` | 看 `[expert type]` 与副职业商店；不要改成 `[material]` |
| 徽章 / 守护珠 | `[avatar emblem]` / `[flag gem]` | 看 `[enchant]`、目标类型、装备限制 |
| 武器防具首饰 | `.equ` + `[equipment type]` | 耐久、`[repair price]`、套装；回收走装备费率 |
| 称号 / 装扮 / 宠物 | `[title name]` `[coat avatar]` `[creature]` | 不要当普通武器改 |

改这些类型时找同类 `.equ` / `.stk`，不要复制药剂字段块。

## 移除不再保留的定义

商城下架与清理定义是两个范围。获准清理时，先解析准确的 ID、路径对应关系，
检查全部保留文件对物品 ID 和定义路径的引用，包括嵌套礼包、商店、任务及文本脚本。
A21 的 Type 1 文件中，整数词元类型为 0，类型 2 是浮点数；Type 3 文件内容为
UTF-16LE 文本。数字命中要结合上下文判断，不能一律当作物品引用。
检查外部引用时，排除本次一起移除的定义。

确认无引用后，同时移除登记和对应定义，保留其他登记及顺序。
打包删除需要重建文件、路径索引及哈希表；把定义清空不等于删除文件。
重新打开输出，核对路径、ID 已不存在，文件数按预期减少，其他文件内容未变。
改动清单同时记录删除的定义路径和修改的登记表。
PVF 引用检查不包含背包、邮件、数据库中已有的道具实例。

## 任务完成的物品奖励

先通过 `n_quest/quest.lst` 解析任务，再精确匹配 `.qst` 的 `[name]`，不能把对话里的名称命中当成任务名。
当 `[reward type]` 为 `[item]` 时，普通 `[reward int data]` 条目按“物品 ID、数量”成对列出固定奖励，
`[reward selection int data]` 是另一个可选奖励列表。奖励 ID 分别经道具或装备登记表核对。
修改数量时保持配对和结束标签，不需要改道具定义或任务目标 `[int data]`。
用满足条件的角色完成任务验收；修改不会自动补发之前已领取的奖励。

当前服务端也支持“物品 ID、`[job]`、职业 ID、转职类型、数量”的职业条件条目，不能按普通配对拆开。
固定物品奖励允许用 ID `0` 表示金币，可选奖励不允许。保留已有特殊条目，改变结构前核对使用端。

## 新增道具

必须同时有：未占用 ID（最终 PVF 的 `.lst` 再查一次）、`.lst` 映射、新定义文件。新名字和新图标不会创造新玩法；服务端必须已支持该使用行为。示例里的占位 ID（如 `123456789`）用前必须重新查重。

### 固定内容礼包 `[cera package]`

`[package data]` 按 **道具 ID、数量** 重复。只接受正数物品 ID，不能写金币 ID `0`。不要和随机 `[booster info]` 混用。装扮礼包常按职业分款。

A21 原有礼包还可能包含 `[package data selection]`，同样按物品 ID、数量成对排列。
核对奖励时，要读取每一个可选奖励段，并和固定、嵌套奖励一起检查；只查
`[package data]` 会漏掉可选奖励。仅上架时保留选择逻辑，进入游戏验证选择界面。

`name_ID` 是本地化占位名称，不代表奖励定义无效。整理显示名称前，要结合实际
本地化文件、礼包内容及明确的系列和职业信息确认。`n_string.lst` 中登记了路径，
也不代表对应本地化文件实际存在。

```text
[stackable type]
	`[cera package]` 0
[package data]
	50 1 3037 100
[/package data]
```

打开后应消耗源道具并发放列表。图标可暂借已有资源。

### 个人金库满级券

整理个人金库升级路线时，先通过 `stackable.lst` 确认
`cash/safe_upgradekit.stk` 和 `safe_upgradekitN.stk` 的物品 ID，再核对说明中的
目标格数及 `cerashop.etc` 对应商品价格。无编号文件是第一档，后续编号对应
后续容量档位。本项目服务端对已识别的高档券直接设置目标容量；购买高档
商城商品按该商品价格扣费，不累加跳过档位的价格。这是服务端实现边界，
仅有 PVF 说明不能证明线上服允许跳级。账号金库工具及
`etc/accountcargo.etc` 应单独分析。

背包用券与商城重复购买的处理不同：券的目标容量已达到时不消耗；当前服务端
购买已达到档位的商城商品，会顺延至下一档并按下一档商品价格收费。下一档
商品缺失时，代码回退到所点击商品的价格。满级后购买被拒绝且不扣费。路线
累计金额应标为“逐级购买合计”，不能当作直接达到目标容量的必付总价。

塞利亚房间的**角色个人金库**，不是账号金库。A21 初始 8 格，最高 200 格。现成功能：ID `10098633`（`cash/safe_upgradekit12.stk`）。

要独立 ID 且稳定指向 200 格：用不同路径创建文件，但文件名保留 `safe_upgradekit12.stk`；服务端按这个文件名识别第 12 档。若改用其他文件名，服务端只会尝试从中文说明中解析受支持的格数，可靠性较低，必须实机验证。已满 200 格不会再消耗。不改变背包栏、装扮栏、账号金库。

## 核对

1. 客户端与服务端加载同一份打包 PVF；重启以清物品缓存。
2. 材料：背包分类、买价、回收价；有兑换则核对扣材料和附加金币。
3. 消耗品：购买、堆叠、使用地点、冷却、实际效果、回收价；说明与效果一致。
4. 期限：用**新实例**看；不要用旧道具判断新 PVF。
5. 新 ID：能识别、图标文案正常、礼包 / 券结果符合服务端已有逻辑。
6. 任务物 / 徽章 / 装备 / 称号 / 装扮 / 宠物：分类、穿戴位置、耐久、外观，以及对应任务或镶嵌功能。
