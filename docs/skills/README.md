## 按任务打开

| 要改什么 | 读 |

| 点券商城上架、售价、页面、契约、商品迁移 | [cera-shop.md](cera-shop.md) |

NPC 商店和道具一起改：先改 `.stk` / `.equ`，再写 `.shp` 上架。
点券商城和道具一起改：同时读商城与道具两份技能，先核对定义和奖励，再改 `cerashop.etc`。
只改上架或售价时，按对应销售系统选择技能，不自动加载其他类别。

技能、副本、怪物、NUT、其他掉落没有独立技能时，仍在有登记表的情况下走对应 `.lst` 读原文。
`etc/` 全局表没有统一登记表；所有任务都遵守下列硬规则。

## 硬规则

- 默认只读。没有明确授权：不写 PVF、不改客户端 ImagePacks2/NPK、不覆盖原版包。
- 数字 ID 不是事实，必须经正确 `.lst` 解析后再读文件。
- 新道具必须同时有空闲 ID、`.lst` 行、定义文件。改名字不会分配 ID。
- 新增块或新文件：先对照同目录、同扩展名、同用途的 2–3 个近邻。不要凭标签名想象格式。
- 保留原有标签、反引号、数值顺序和成对 `[/...]`；可编辑文本保留空白。
  Type 1 二进制 PVF 可能规范化回读的空白，应比较解析后的内容与顺序，并说明排版限制。
  不要把文档示例粘成完整文件。
- `.shp` 只上架。价格、绑定、效果、期限在道具文件。
- `[explain]` 是说明文字，不等于效果。图标路径不证明客户端资源存在。
- 重写打包 PVF 时，必须用 PVF 解析/写入工具：先保存临时档案、回读验证，最后原子替换已授权目标；不能把 PVF 当文本改。
- 写完必须读回。行为结论要说明实机怎么测。客户端和服务端加载同一份新 PVF；重启服务端是已确认的缓存清理方式，重载只在部署环境已验证支持时使用。
- 查询或修改确认了新的可复用知识，交付前同一轮更新对应技能/AGENTS.md 及中文页。
  直接记录操作规则和字段含义，保留必要的版本/运行环境范围；不写来源叙述、历史案例、
  参考包名称、一次性数值或不确定的解释，不依赖旧任务附件。新主题补齐两边入口。

## 字符串编码检查

本项目 A21 格式的 Type 1 字符串引用通过偏移的最低位区分窄字符串表 `sTrA`
和 UTF-16LE 表 `sTrW`。窄表可能包含旧式 GBK 字节，不能一律按 UTF-8 解码。
排查乱码时，比较原始字节以及来源字符串的引用类型。

迁移中文文本时保留 Unicode 引用；写入器复用字符串缓存时，可能选中窄表同名文本，
丢失来源中的 Unicode 表示。强制 Unicode 写入后检查引用偏移最低位为 1；
允许回退到窄表缓存的“优先 Unicode”选项不足以保证这一点。
名称和说明必须按使用端的解码方式验证，不能只依赖写入器自己的回读。
损坏文本从完整来源恢复，不猜字替换。

## 本项目输出与改动清单

- 保留输入包和基线包。没有另外指定时，新包放在本项目 `dist/`，名称为
  `Script_yyyyMMdd_HHmmss.pvf`，使用北京时间（UTC+8）。先写临时包并回读验证，
  再发布新文件；同名已存在时使用新时间，不覆盖已有输出。
- 实际修改 PVF 时，继续使用同一个 `dist/改动清单.xlsx`，保留旧工作表，按修改功能新建工作表。
  A1 记录交付的 PVF 文件名，A2 简述改动内容，第 3 行为明细表头。
  A3 固定为“路径”，第 4 行起逐行记录实际修改或新增的 PVF 内路径，并去重。
  特殊改动有必要时可增加已核实的补充列，例如新增 ID 范围、兑换规则；文件路径始终必填。
  同名功能工作表已存在时加唯一后缀，并告知实际名称，不能替换历史记录。
- 核对工作表路径集合与实际改动一致，包含改动的登记表和配置文件。
  仅修改技能/文档不新增 PVF 改动工作表；历史商品支持分析表不作为改动清单更新。

## 流程

```text
只读闭合 →（授权后）最小改动 → 读回 → 打包匹配的客户端/服务端 PVF → 实机验收
```

1. 确认改的是 NPC / 道具 / 商店 / 其他，以及这次能不能写。
2. 用名称或 ID 走对应 `.lst`，读目标文件，不要靠文件名猜。
3. 列出路径、字段、旧值、新值，以及商店、配方、任务、礼包等依赖。
4. 获授权后再改，只改计划内字段。
5. 读回改动文件和相关 `.lst`。
6. 记录：改了什么、没改什么、打包注意、实机怎么验、旧道具实例会不会自动刷新。
